# 00. Видение

## Базовая формулировка

> Любая длительная агентная задача может быть представлена как траектория в пространстве состояний между
> текущим состоянием и множеством состояний, удовлетворяющих критериям цели. Контекст, подзадачи,
> неопределённость, зависимости и вычислительные затраты формируют геометрию этого пространства.
> Эффективность агента определяется не объёмом произведённого контекста, а скоростью сокращения
> проверяемого расстояния до цели относительно затраченных вычислительных ресурсов.

## Исходная интуиция и её уточнение

| Исходная метафора | Уточнение |
|---|---|
| Две точки на прямой: CURRENT ● ─── ● GOAL | Пространство состояний `S_t = (P, C, N, U, R, K, D, …)`; цель — область `G ⊆ S` |
| Размер точки = объём контекста | Радиус `r = f(|C|)` + внутренняя структура: useful / redundant / stale / conflict → плотность `ρ` |
| Толщина линии = загрязнённость | Context Friction `F = f(N, R, H, X)` |
| Больше сабтасков → быстрее к цели | **Неверно в общем случае**: существует оптимальная гранулярность `n*` (U-кривая стоимости) |

Главное разделение: **размер контекста ≠ прогресс ≠ сложность задачи**.

## Названия
- **Agentic State Geometry** — теория.
- **Geometric Context Controller (GCC)** — реализация контроллера.
- **Agent Geometry Observatory** — интерфейс мониторинга.

## Три компонента + интерфейс

`Observer → Geometry Engine → Controller`, поверх — `Observatory`. См. `02_architecture/overview.md`.

## Главная научная проблема

Как измерить `D(S, G)`. Ответ проекта: `D = (D_completion, D_cost, U_D)` с опорой на verifiers и Git-evidence.
См. `01_theory/distance_to_goal.md`.

## Критерий успеха идеи

Геометрические метрики **предсказывают деградацию агента раньше**, чем он провалит задачу, и контроллер
на их основе улучшает success rate / tokens-to-success. См. `03_experiments/experiment_plan.md`.

## Дорожная карта
1. **Этап 0** — каркас, формулы, пороговый контроллер (текущий).
2. **Этап 1** — Observer для одного агентного фреймворка + Git evidence; логирование траекторий.
3. **Этап 2** — офлайн-анализ: предсказывают ли метрики провалы (без вмешательства).
4. **Этап 3** — A/B: агент vs агент + контроллер на 30–100 long-horizon задачах.
5. **Этап 4** — Observatory (радар проекта), управление Git-стратегией (split/merge PR).
